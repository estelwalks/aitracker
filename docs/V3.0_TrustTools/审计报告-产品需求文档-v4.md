## 关键问题（必须修复）

### K1: FR-001 与 Section 8 成功指标数据矛盾 🔴

- **FR-001（第 97 行）：** `支持 Claude Code、Cursor、Codex、Gemini CLI、Kimi Code 等 20+ 工具`
- **Section 8 成功指标（第 626 行）：** `支持 AI 工具数 | 0 | 10+`
- **需求简报：** `覆盖 10+ 主流 AI 工具的 token 解析`

三处数字不一致（20+ vs 10+ vs 10+）。PRD 内部自相矛盾，且与简报不一致。

**修复：** 统一为一个数字。建议按简报口径统一为 10+（MVP 实际可达），20+ 留给 V1.1。

---

### K2: FR-019 验收标准含技术实现细节 🔴

- **FR-019（第 376 行）：** `支持 npm 包一键启动（npx trusttools）`
- **FR-019（第 375 行）：** `Windows 提供 .exe (NSIS) 安装包`

`npm`、`npx`、`NSIS` 是实现细节，违反了 D3 范围边界原则。产品需求应描述"支持命令行一键启动"而非指定具体包管理器。

**修复：** `npm 包` → `命令行包`，`npx trusttools` → `一行命令启动`，`NSIS` → 删除（安装包格式是实现细节）。

---

### K3: STORY-24（浏览器模式）缺少对应 FR 🔴

EPIC-06 中 STORY-24 为"作为用户，我想在浏览器里直接打开使用，不用装桌面壳"，但 traceability matrix 中无 FR 映射到 STORY-24。FR-019 涵盖浏览器模式但仅映射到 STORY-21。

**修复：** 在 traceability matrix 中新增一行 `FR-019 | 桌面客户端 | EPIC-06 | STORY-24 | MUST`（FR-019 可映射多个 Story），或将浏览器模式拆为独立 FR。

## 警告

### W1: NFR-016"设计感"不可测量 🟡

- **NFR-016（第 429 行）：** `海报需有设计感`

"设计感"是主观判断，无法客观验证。虽然补充了"至少 2 套视觉模板、1080×1920 竖版 PNG、带品牌标识"等可测量标准，但"设计感"本身仍然是模糊词。

**建议：** 删除"有设计感"表述，改为"海报需通过 5 人内部评审认可"或直接依赖模板数量+尺寸的硬性标准。

---

### W2: 记忆模块（EPIC-05）需求过于单薄 🟡

作为 6 大模块之一，记忆仅分配了 FR-017（目录配置）和 FR-018（浏览）2 个功能需求，以及 STORY-19/20 两个用户故事。相比之下 Token 管理有 5 个 FR、Skill 管理有 4 个 FR。

**建议：** 明确记忆模块在 MVP 阶段的最小范围（当前够用），或将 FR-017/FR-018 合并，不单独成 Epic。

---

### W3: 缺少升级机制需求 🟡

PRD 未定义用户如何获取新版本。桌面客户端通常需要：
- 版本更新通知
- 自动/手动更新
- 更新失败回滚

**建议：** 至少新增 1 条 SHOULD 级别的升级需求（如 FR-xxx: 版本更新检测与通知）。

---

### W4: 缺少安装包体积约束 🟡

作为桌面端分发产品（.dmg/.exe），安装包体积直接影响下载转化率。PRD 中未设定体积上限。

**建议：** NFR 中补充安装包体积上限（如 < 200MB），作为打包阶段的硬性约束。

---

### W5: 安全检测 AI 审查层依赖未声明 🟡

FR-010 要求"AI 审查作为第二层验证"，但：
- 未说明使用什么 AI 模型
- 未说明是否需要用户自带 API Key
- 未说明 AI 不可用时的降级策略（是否仅靠静态规则继续？）

虽然需求简报 Q5 提到了这个问题，但 PRD 本身应在依赖项中记录此不确定性。

**建议：** 在 Section 9 依赖表中新增一行：`Skill 安全检测 AI 审查模型 | AI 服务 | 待定 | 中——影响安全检测准确率和成本`。
