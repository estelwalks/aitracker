## 1. 执行摘要

当前版本已经具备完整的产品外形：七个主要页面均可访问，Token 数据、Skill、本地市场、安全检测、Memory、主题和海报等模块都有不同程度的真实实现，类型检查与生产构建也能够通过。因此，它已经超过“纯原型”阶段，适合继续作为内部开发版本。

但当前版本还不能作为 PRD v3.2 的可发布 MVP。问题并非只集中在少量按钮或页面缺失，而是存在几项会影响数据可信度、隐私承诺和桌面产品稳定性的系统性风险：

1. **核心统计维度语义错误。** PRD 中的 Provider 指 Anthropic、OpenAI 等模型供应商；首页和 Token 页却把 Claude Code、Codex、Cursor 等客户端来源标为 Provider。核心图表、预算和海报由此可能向用户表达错误结论。
2. **Electron 持久化设计失效。** 桌面端每次启动使用随机 localhost 端口，而设置、主题、布局和每日检测额度依赖按 origin 隔离的 `localStorage`，导致应用重启后可能全部恢复默认，检测次数也可通过重启重置。
3. **TokenTracker 集成违反项目当前 Clean Room 与架构基线。** 打包产物直接携带并运行 TokenTracker CLI，还会在 Electron 首次同步后无单独授权地执行初始化 Hook。这既与“只研究行为、独立实现 Adapter”的内部约束冲突，也可能修改用户其他 AI 工具的配置。
4. **安全检测并非 PRD 描述的双层审查。** AI 默认关闭，且只接收静态规则已经命中的片段；没有静态命中时 AI 看不到内容，不能独立发现混淆或新型风险。市场安装也只执行静态扫描。
5. **实现与当前架构决策相反。** 最新架构要求 Renderer → Preload → Main → Utility Process → SQLite，明确放弃 localhost 服务化后端；实际业务扫描、解包、市场安装和外部 CLI 均运行在 Electron Main 加载的 localhost Nitro 服务中。
6. **多项设置是“保存成功但业务不生效”。** 预算、自动发现、监控目录、Skill 健康阈值、Memory 排除目录等都有可操作界面，但未进入实际扫描或计算链路。
7. **PRD MUST 项仍有整项缺失。** 中英文切换 FR-022 和自动更新 FR-025 尚未实现；Skill 更新、CLI 启动入口、签名发布等也未闭环。
8. **工程交付不可复现。** 当前 `package-lock.json` 会使多个 npm 主版本下的 `npm ci` 均报 `Invalid Version`；lint、单测和 E2E 门禁也没有达到可发布状态。

### 1.1 功能覆盖结论

按 FR-001～FR-025 的验收标准进行严格追踪：

| 状态       | 数量 | 占比 | 功能                                          |
| ---------- | ---: | ---: | --------------------------------------------- |
| 已完整实现 |    3 |  12% | FR-013、FR-018、FR-023                        |
| 部分实现   |   20 |  80% | FR-001～012、FR-014～017、FR-019～021、FR-024 |
| 未实现     |    2 |   8% | FR-022、FR-025                                |

“部分实现”不等于完成度 80%。其中包含页面已存在但核心验收语义错误、设置未生效、只有静态扫描却被描述为双层扫描等情况，不应直接计入可验收功能。

### 1.2 优先级定义

| 级别 | 定义                                                                                    |
| ---- | --------------------------------------------------------------------------------------- |
| P0   | 影响数据真实性、用户设备安全、隐私承诺、基础持久化或可重复交付；外部试用/发布前必须解决 |

## 2. 发布阻断问题（P0）

### P0-01：TokenTracker 运行时与自动 Hook 违反当前项目约束

**事实**

- PRD NFR-013、`docs/compliance/CLEAN_ROOM.md` 和新版架构均要求独立实现，只研究外部项目的可观察行为与公开数据格式。
- 新版架构明确写明：不使用 TokenTracker CLI、本地 API、UI、文件结构、 queue/cursor schema、函数接口和测试。
- `electron-builder.yml` 将 `vendor/tokentracker-cli` 及其 `node_modules` 直接打入应用。
- `src/lib/local-usage/tokentracker-bridge.server.ts` 直接启动该 CLI，并读取其 `.tokentracker/tracker/queue.jsonl`。
- Electron 首次同步后会后台执行 `init --yes --no-auth --no-open`。
- 被打包 CLI 的 `init` 会探测并修改 Codex、Claude、Gemini、OpenCode 等工具配置或 Hook。
- 现有相似度报告仅扫描 TrustTools 的 `src`，未覆盖仓库中的 `vendor`，因此其“0%”结论不能证明当前交付物符合项目自定的 Clean Room 规则。

**影响**

- 当前实现与项目自身的合规声明、架构基线直接冲突。
- 应用可能在没有逐 Provider 明示授权的情况下修改其他 AI 工具配置。
- TrustTools 卸载后可能残留指向已不存在运行时的 Hook。
- 供应链、许可证、NOTICE、升级兼容和故障责任边界不清晰。

**建议**

1. 发布前移除打包的 TokenTracker 运行时、queue 依赖和自动 `init`。
2. 对每个数据源实现独立、最小化、只读优先的 Source Adapter。
3. 被动采集确实不能满足时，才为单个来源提供默认关闭的 trigger-only Hook。
4. Hook 启用前展示目标配置、变更内容和隐私说明；写入前备份，提供检测、恢复和卸载清理。
5. 重新执行覆盖整个交付物的许可证、NOTICE、来源和相似度审查。

**验收口径**

- 安装与首次启动不修改任一第三方 AI 工具配置。
- 未授权时不存在 TrustTools/TokenTracker Hook。
- 卸载或禁用 Hook 后配置可完整恢复。
- 构建产物中不再包含被禁止复用的 CLI、queue schema 或运行时。

### P0-02：随机 Electron origin 导致设置和每日额度跨重启失效

**事实**

- `electron/local-web-server.ts` 使用 `server.listen(0, "127.0.0.1")`，每次启动获得随机端口。
- Electron 加载的页面 origin 因端口变化而变化。
- `src/lib/settings/store.ts` 将预算、目录、阈值、规则等设置保存在 `localStorage`。
- 主题、Dashboard 布局和 FR-011 每日检测次数也保存在 `localStorage`。

**影响**

- 重启后主题、布局、预算、扫描目录、安全规则等可能恢复默认。
- 每日 10 次限制可通过重启桌面应用重置。
- 同一用户在浏览器模式与 Electron 模式之间也没有统一配置事实源。
- 直接违反 FR-004、FR-011、FR-013、FR-017 的持久化预期。

**建议**

- 将设置、额度、扫描任务状态和必要历史统一存入 `app.getPath("userData")` 下的 SQLite 或原子配置文件。
- 每日额度由服务端事务性消费，不把限制边界放在 Renderer。
- UI 只通过类型化应用服务读写配置。
- 如果暂时继续使用 Web Storage，至少使用稳定受控 origin/custom protocol；但这不应成为长期额度方案。

**验收口径**

- 连续重启 20 次，端口或运行方式变化不影响所有设置、主题、布局和剩余额度。
- 浏览器刷新、窗口关闭、托盘隐藏、应用升级均不导致配置丢失。
- 同一检测任务只能原子扣减一次。

### P0-03：核心运行时与最新架构决策相反，缺少故障隔离

**事实**

- `docs/V3.0_TrustTools/示意图/TrustTools-V3.0-架构设计文档.md` 要求 Main 不承载领域业务、SQLite 为事实源，并采用 Utility Process。
- 同一文档明确将“全部业务放 Electron Main”和“localhost 服务化后端”列为放弃方案。
- 实际 Electron Main 动态加载 Nitro server；Token 扫描、Memory 扫描、压缩包解包、市场安装和 TokenTracker 子进程均由该运行时执行。
- 当前没有 Utility Process、MessagePort 任务协议、统一 SQLite 领域仓库、任务监管、崩溃重启或事务回滚。
- Token 事实源实际为保存大量事件的 JSON 文件。

**影响**

- 大文件、异常正则、同步解包或外部 CLI 卡死可能拖累窗口和托盘生命周期。
- 架构 QA 中的任务取消、超时、崩溃恢复和事务一致性没有实现基础。
- 文档和代码无法共同作为研发与验收基线。

**建议**

- 优先按已批准架构迁移：Renderer → 白名单 Preload → Main → Utility Process → SQLite WAL。
- 为长任务建立类型化协议、进度、取消、超时、资源上限和崩溃恢复。
- 如果团队决定保留 localhost Nitro，则必须先用 ADR 正式推翻现有架构，并补齐新的威胁模型、资源测试与能力鉴权设计。

**验收口径**

- 任一扫描/解包/外部 CLI 进程崩溃不影响窗口、托盘和其他任务。
- 长任务可取消、可超时、可恢复，并具有可观察状态。
- 架构文档、ADR、实际进程边界和自动化架构测试一致。

### P0-04：localhost 能力接口缺少鉴权和资源边界

**事实**

- 服务只绑定 `127.0.0.1`，这是正确的基础防护。
- 但没有随机 capability token、细粒度权限、请求速率限制或严格 Host/Origin 白名单。
- 非 GET 请求体和 Nitro 响应均会被整体读取进内存，未看到明确大小限制。
- 服务可以访问本地 Token、项目、会话、Memory 正文，并执行 Skill 安装/删除。
- 已有 CSRF 中间件能降低普通网页跨站调用风险，但不能替代同机进程的能力鉴权。

**影响**

- 同机低权限进程发现端口后，可能访问本地数据或调用有副作用的能力。
- 超大请求/响应可能造成 Main 进程内存压力。

**建议**

- 首选类型化 IPC 和 Utility Process。
- 若保留 HTTP：每次启动生成不可预测 bearer capability；严格校验 Host/Origin；按读、写、删除分级授权；限制请求/响应体；增加速率限制和审计日志。

### P0-05：Provider 核心语义错误

**事实**

- PRD 定义 Provider 为 Anthropic、OpenAI 等模型供应商，并要求 Provider → 模型 → 会话下钻。
- `src/routes/index.tsx` 和 `src/routes/tokens.tsx` 实际使用 `snapshot.bySource`/`source`，数据值为 Claude Code、Codex、Cursor、Aipy 等客户端，却在 UI 中标记为 Provider。
- 浏览器实测首页 Provider 面板显示的正是这些客户端名称。

**影响**

- 费用归因、占比、预算预警、趋势图和海报的业务含义错误。
- 同一 Provider 被多个客户端调用时无法正确聚合。
- 用户会把“客户端来源”误解为“模型供应商”。

**建议**

建立清晰的数据模型：

`AI 客户端/Agent → Provider → 模型 → 项目/会话`

其中：

- Client/Agent：Claude Code、Codex、Cursor 等。
- Provider：Anthropic、OpenAI、Google、DeepSeek、Moonshot、xAI 等。
- Model：具体模型标识。
- 未能可靠推断 Provider 时显示“未知”，不要退化为客户端名称。

**验收口径**

- 相同模型通过两个客户端使用时，Provider 总额正确合并，Client 维度仍可分别查看。
- 所有图表、预算、下钻、导出和海报使用同一字段字典。
- 通过官方账单样本验证 Provider 与费用聚合。

### P0-06：安全检测被表达为双层审查，但 AI 不能独立发现风险

**事实**

- AI 审查默认关闭。
- AI 只接收本地静态规则已经命中的脱敏片段。
- 没有静态命中时，AI 看不到代码，无法独立识别混淆、跨文件逻辑或未知模式。
- AI 返回内容只补充摘要，不改变最终 verdict。
- 市场安装只执行静态扫描；warning 通常仍会直接安装。
- 检测额度在文件格式、大小和可读性验证之前消费。

**影响**

- FR-010“静态规则 + AI 深度检测”没有实质成立。
- 页面文案可能让用户高估检测覆盖。
- 失败选择也扣次数，且 UI 显示“已用”而不是 PRD 要求的“剩余”。
- “安全后安装”的用户决策点缺失。

**建议**

产品必须先选择并明确一种可验证语义：

1. **纯本地静态扫描**：诚实标注覆盖边界，不称为 AI 双层审查；或
2. **可选云端复核**：用户明确授权，定义发送字段、地域、日志保留和断网降级；AI 独立接收受控的完整分析材料；或
3. **本地模型审查**：定义模型体积、资源要求和准确率。

市场链路应改为：

`下载到隔离区 → 扫描 → 展示报告 → 用户确认 → 原子安装/回滚`

### P0-07：Dashboard 手机端发生真实内容重叠

**事实**

- React Grid Layout 在 `xs/sm` 给 KPI widget 固定高度。
- CSS 在 599px 以下将四张 KPI 卡改为单列，但外层网格高度没有同步增长。
- 375px 浏览器实测 KPI 第四张卡底部约为 653.5px，而后续趋势组件顶部约为 385.5px，重叠约 268px。
- 1280px 窗口的内容区宽度也可能进入 RGL 的 `sm` 断点，而 CSS 仍按视口采用四列，产生明显空洞。

**影响**

- 手机端首页核心内容不可读、不可操作。
- 布局高度与真实内容脱节，也会影响拖拽和后续组件位置。

**建议**

- 小屏关闭 RGL 固定行高与拖拽，使用普通文档流。
- 断点以内容容器宽度为准，不混用 viewport CSS 与 container RGL 断点。
- 为 375、390、768、1024、1280、1440px 建立视觉回归和元素不相交断言。

### P0-08：依赖锁文件损坏，无法进行可重复安装

**事实**

- `npm ci` 在 npm 10、11、12 下均报 `Invalid Version`。
- 问题与 `package-lock.json` 内部分嵌套平台包缺少合法版本有关。
- 本轮只能使用 `npm install --package-lock=false --ignore-scripts` 临时安装依赖后完成验证；未修改已跟踪锁文件。

**影响**

- CI、新开发机和发布机不能从锁文件重复构建。
- 当前“构建通过”只证明临时解析出的依赖集合可构建，不证明锁定版本可交付。

**建议**

- 在受控 Node/npm 版本下重新生成并审查锁文件。
- CI 首步只允许 `npm ci`，禁止静默回退到无锁安装。
- 记录 Node/npm 版本，构建产物生成 SBOM 和依赖许可证清单。

## 5. 设计与交互审计

### 5.1 Dashboard

**关键问题**

- UI-001/FR-020 要求的第五张“安全检测剩余次数”卡片缺失。
- 首页没有“生成海报”入口。
- 默认展示“近 7 天 Token / 区间费用”，与 PRD“今日 Token / 本月费用”不一致。
- 自定义区间在代码中存在，但选项被 `slice(0, 5)` 排除。
- 预算预警计算存在却未渲染。
- 移动端网格发生真实重叠，桌面特定宽度又出现空洞。
- Dashboard 可拖拽，但缺显式手柄说明、锁定状态和键盘替代。

**建议**

- 先冻结首页 5 个核心指标及默认时间口径。
- Provider/Client 语义修正后再做图表视觉优化。
- 小屏改为普通文档流；桌面拖拽仅在足够宽度开启。
- 将预算预警、安全剩余次数和海报入口纳入首页验收截图。

### 5.2 Token 分析

**关键问题**

- 五条下钻链没有形成统一树，更多是单表展开。
- 可排序 `<th onClick>`、可展开 `<tr onClick>` 不支持键盘，也没有 `aria-sort`/`aria-expanded`。
- 搜索框只有 placeholder，无可访问 label。
- 大量会话一次性渲染；实测本地 13,420 条事件时页面很长，缺分页/虚拟化。
- 币种刷新后恢复 CNY，且与 Dashboard 不共享。

**建议**

- 用统一的 drilldown contract 生成 Client、Provider、Model、Project、Session 视图。
- 对长会话列表分页或虚拟化。
- 将排序、展开改为真实按钮并补齐 ARIA。
- 币种进入全局设置和统一费用服务。

### 5.3 Skill 管理与市场

**关键问题**

- 健康度算法、Agent 清单和黑名单行为均与 PRD 不一致。
- 市场卡片长期显示“版本未提供”。
- “可更新”没有更新动作。
- 安装前没有真正的报告审阅与用户决策步骤。
- 多目标安装无原子事务，失败后可能形成部分状态。
- 市场和 Skill 卡片多为可点击容器，缺键盘操作。
- Modal 无 `role=dialog`、焦点圈定、Escape 关闭；实测打开后焦点仍在 `BODY`。

**建议**

- 先完成版本、内容哈希、本地修改状态模型，再实现更新。
- 安装向导拆成目标选择、隔离扫描、报告确认、安装结果四步。
- 为部分安装建立 rollback journal。
- 卡片主操作使用 button/link，Modal 使用成熟的可访问 Dialog 组件。

### 5.4 安全检测

**关键问题**

- 缺扫描进度条和阶段状态。
- 额度先扣后校验，且“今日已用”与需求“今日剩余”相反。
- 安全报告后没有“一键安装”。
- 历史只存在当前页面 state，离开页面即丢失。
- 自定义 JavaScript 正则可能出现灾难性回溯，扫描又在 Renderer 侧执行。

**建议**

- 文件通过基础校验且任务创建成功后再原子扣次。
- 扫描放入有超时和取消能力的受限 Worker/Utility Process。
- 报告显示扫描引擎、规则版本、覆盖范围和未检查项。
- safe/warn/block 都要有明确下一步，不把“分数”当作绝对安全结论。

### 5.5 Memory

**关键问题**

- 首次进入页面无视用户设置，直接扫描默认目录。
- 默认把仓库 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 作为 Memory，并展示绝对路径和正文。
- 自定义目录中的任意 Markdown 都可能被纳入。
- `memoryExcludes` 未接入服务。
- 完整正文先返回 Renderer，而不是用户展开时按需读取。

**建议**

- 首次扫描前展示范围预览并获取授权。
- 明确区分“AI Memory”“项目指令”“普通 Markdown”。
- 默认只索引 metadata/摘要，展开时再读取正文。
- 目录开关、排除规则、来源授权在服务端持久化并于初始 loader 生效。

### 5.6 设置页

当前设置页同时包含普通偏好、高级 Adapter 探测、原始 JSON 和研发诊断信息，信息层级过重。更严重的是多项设置并不生效。

建议拆成：

1. 常规：语言、主题、币种、启动、更新、隐私。
2. 数据源：Token、Skill、Memory 的目录和授权。
3. 预算与规则：费用预算、安全规则、健康阈值。
4. 高级/诊断：Adapter 探测、原始数据、日志与导出。

未接通的选项应隐藏或明确标记“尚未生效”，不能保存后给出成功错觉。

### 5.7 可访问性与状态反馈

**主要缺口**

- Segmented 选中态只靠颜色，没有 radio/tab/`aria-pressed` 语义。
- 多处卡片、表格行和列表项只能鼠标点击。
- 图表没有等价文本/表格。
- 多处 8～11px 次要文字，对比度和可读性不足。
- 通用按钮 28/32px，不适合移动触控。
- 未提供 `prefers-reduced-motion` 降级。
- 路由缺 Skeleton/pending state；部分错误被静默吞掉。
- 错误/警告区域缺 `role=alert`，加载区缺 `aria-busy`。
- Google Fonts 是所有页面的启动时网络依赖，与离线和隐私定位不协调。

**建议**

- 以 WCAG 2.2 AA 为验收基线。
- 优先修复键盘导航、焦点管理、语义控件、对比度和触控目标。
- 使用系统字体或内置字体，避免本地核心页面依赖外网。

## 6. 架构、数据与隐私审计

### 6.1 文档基线漂移

仓库同时存在两套方向明显不同的架构文档：

- `docs/V3.0_TrustTools/TrustTools-V3.0-架构设计文档.md` 仍描述登录、团队、浏览器插件、固定 localhost:7680、JSONL + SQLite 和大量 API。
- `docs/V3.0_TrustTools/示意图/TrustTools-V3.0-架构设计文档.md` 明确采用本地多进程模块化单体、Utility Process、SQLite，并放弃 localhost 服务化后端。
- README 前文说生产 Electron 使用随机 localhost，后文又说 Electron 不需要 localhost；还声称 Skill/市场/安全/Memory 使用 mock，与当前代码不符。

**建议**

- 指定唯一的“当前有效”PRD、架构、ADR、数据字典和验收矩阵。
- 将旧文档移动到 `archive/` 并在页首标记失效日期与替代文档。
- 任何架构偏离必须先有 ADR，再进入实现。

### 6.2 后台采集并不持续

根路由只在页面可见且当前位于 `/` 或 `/tokens` 时刷新；Skill 页面也是可见时轮询，不是独立后台采集任务。窗口隐藏到托盘或停留其他页面时，数据不会持续更新。

这与 FR-021“应用启动时自动开始，退出时停止”和“本地后台运行”不一致。

建议将采集调度放入 Utility Process，UI 只订阅：

- 当前状态与数据新鲜度；
- 上次成功时间；
- 正在扫描的来源和进度；
- degraded/失败原因；
- 手动重试和取消。

### 6.3 数据最小化与归因可信度

实际实现除模型、Token 数和时间外，还会处理或持久化 project、session、工具、Skill、命令签名和输出大小摘要。Codex 解析过程会读取命令参数/输出，再生成摘要。

此外，工具/Skill Token 归因存在“把一个事件的 Token 均分给各工具”的启发式算法，但 UI 容易让用户理解为精确测量。

建议：

- 建立字段级数据字典：来源、用途、是否落盘、保留期、导出/删除方式。
- 对启发式归因明确标注“估算”和算法版本。
- 关键聚合用官方账单/golden fixtures 验证，不展示无法证明的精度。

### 6.4 市场安装事务

当前多目标安装逐项执行，缺少：

- 隔离区；
- 内容哈希与签名；
- 扫描后用户确认；
- 原子提交；
- 部分成功回滚；
- 更新冲突处理；
- 卸载时配置清理。

建议为每次安装生成 transaction journal，完整记录下载哈希、扫描报告、目标路径、备份、写入与回滚状态。

### 6.5 桌面分发

当前：

- `package.json` 为 private，无 CLI `bin`；
- 无自动更新代码；
- 自启动默认关闭；
- builder 引用被 `.gitignore` 忽略的图标资源；
- macOS afterPack 仅 ad-hoc 签名，无 Developer ID/notarization；
- Windows 无签名配置；
- 无 Electron/macOS/Windows 安装、托盘、自启、更新自动化测试。

因此 FR-019、FR-024、FR-025 目前不能按“可交付”验收。

### 7.2 测试体系问题

1. `package.json` 没有统一 `test` script，但发布检查表要求执行 `npm test`。
2. lint 覆盖 vendored 代码，数千格式错误掩盖真正问题，门禁失去可操作性。
3. `src/routes/-index.test.ts` 在 Node runner 中直接引入 `react-grid-layout` CSS，导致测试失败。
4. E2E 仍断言已经不存在的文案，例如“整体费用预算预警”。
5. E2E 依赖用户真实 HOME、真实 Skill/Memory、本地历史和公网市场，不能稳定复现。
6. 测试中仍硬编码旧 Adapter 数量，与实际已知来源清单不一致。
7. 缺少 Electron、macOS、Windows 的安装、托盘、自启、随机端口持久化和自动更新测试。
8. 缺少国际化、海报导出、市场安装回滚、权限授权和离线模式的端到端测试。
9. NFR 的 Token 准确率、首次数据时间、内存占用、安装包大小均没有发布门禁。

### 7.3 建议的发布质量门禁

合并或发布前至少要求：

```text
npm ci
lint
typecheck:web
typecheck:electron
unit
contract/golden-fixture
performance
web-e2e
electron-e2e
package:mac + signed smoke
package:win + signed smoke
offline/privacy smoke
```

所有测试必须使用隔离的临时 HOME、固定 fixture 和 mock server，不得修改开发者真实 AI 工具配置。

## 9. 建议的整改顺序

### Gate 0：冻结唯一产品与架构基线

在继续扩展功能前完成：

1. 冻结 Provider/Client/Model/Project/Session 数据字典。
2. 决定 AI 审查是纯本地、可选云端还是本地模型，并修正隐私承诺。
3. 决定 TokenTracker 清退方案和 Hook 授权策略。
4. 冻结首发数据源、Skill 目标 Agent 和版本范围。
5. 明确 10 次/天、市场扫描和安装阻断规则。
6. 明确 Memory 扫描授权和数据生命周期。
7. 指定唯一有效 PRD、架构和 ADR；归档冲突文档。

**退出条件：** 上述每一项都有负责人签字的决策记录和可测试验收口径。

### Gate 1：修复数据可信、持久化和安全边界

1. 移除 TokenTracker 运行时与静默 Hook，改为独立 Adapter。
2. 将配置、额度和任务状态迁移出 localStorage。
3. 修正 Provider/Client 数据模型及所有图表、预算和海报。
4. 建立 Utility Process/SQLite/任务协议，或以 ADR 确认替代架构。
5. 为本地能力接口补充鉴权、大小限制、超时、取消和审计。
6. 重做安全扫描/市场安装的隔离、报告确认和回滚链路。
7. 修复 Dashboard 小屏重叠。

**退出条件：** 数据聚合通过 golden fixtures；应用跨重启设置不丢；安装不静默修改外部配置；安全任务可取消/回滚；375～1440px 无布局重叠。

### Gate 2：关闭 PRD MUST 缺口

1. 接通预算、目录、阈值、Memory 排除和币种设置。
2. 完整实现五条 Token 下钻链。
3. 按 PRD 算法实现 Skill 健康度与目标 Agent。
4. 实现市场版本、更新、差异、保留本地修改和回滚。
5. 实现中英文切换。
6. 实现真实后台采集状态。
7. 实现浏览器 CLI 与自动更新。
8. 补齐首页第五 KPI、海报入口和安全剩余次数。

**退出条件：** FR-001～FR-025 中所有 MUST 项均有对应自动化验收，不再存在“设置可保存但业务不生效”。

### Gate 3：建立可重复桌面发布能力

1. 修复 lockfile，使 `npm ci` 成为唯一安装路径。
2. 清理 lint 范围和所有有效错误。
3. 建立隔离、确定性的单元/契约/E2E fixture。
4. 加入 macOS/Windows 签名、公证、安装、托盘、自启、更新和卸载清理测试。
5. 验证 NFR：准确率、首次数据时间、查询性能、内存、安装包大小、离线与隐私。

**退出条件：** 从干净环境可一键生成经过签名验证的安装包，所有门禁通过，发布清单与实际脚本一致。

## 10. 推荐的下一版 MVP 范围

当前范围过大。建议把首个可信版本收敛为：

### MVP-A：本地 Token 数据可信版

- 5～8 个有真实 fixture 的高优先级 Client/Provider；
- 明确 Client/Provider/Model 语义；
- Token、费用、项目/会话下钻；
- 统一设置持久化；
- Dashboard 与海报；
- 本地后台采集、数据新鲜度和导出/删除；
- macOS 单平台签名内测。

### MVP-B：Skill 管理与安全版

- 真实健康度；
- 明确的目标 Agent 清单；
- 本地静态安全扫描；
- 回收站、黑名单管理；
- 隔离安装、报告确认和回滚；
- 市场版本与更新。

### MVP-C：完整分发版

- Windows；
- 中英文；
- 浏览器 CLI；
- 自动更新；
- 可选 AI 审查；
- 更广的数据源与 Memory 管理。

这种拆分能先验证最核心的“数据是否可信”，再叠加高风险的安装、安全和云端能力。

## 11. 最终结论

当前代码不是“没有实现”，而是已经形成了一个功能丰富的内部 Alpha；问题在于它的实现深度与 PRD 宣称的完成度不匹配，且存在数据语义、持久化、合规和架构边界上的发布级风险。

建议当前版本保持 **内部开发状态**，不要以 PRD v3.2 的 MVP 名义验收。下一步不宜继续横向增加功能，而应先完成 Gate 0 的产品与架构决策，再依次修复：

1. TokenTracker/Hook 与 Clean Room 风险；
2. Electron 设置持久化；
3. Provider/Client 数据语义；
4. 安全扫描与市场安装真实闭环；
5. 运行时故障隔离；
6. 可重复构建和发布门禁。

完成这些基础项后，现有 UI、数据适配、市场缓存、受限解包、主题和海报能力都可以继续复用，项目不需要推倒重来，但需要一次明确的“从演示可用到发布可信”的收敛迭代。
