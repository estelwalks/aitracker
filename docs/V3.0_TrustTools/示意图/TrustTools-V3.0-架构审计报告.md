## 2. 审计结论

**结论：NEEDS REVISION（暂不批准进入全面实施）。**

当前架构方向合理：全栈 TypeScript、Electron 多进程模块化单体、Utility Process 单写 SQLite、类型化 IPC、Adapter 采集内核以及 TokenTracker Clean Room 边界均符合项目约束。审计未发现 P0 级方向性错误。

PRD v2.3 已移除 Python/Electron/Stack 等技术选型描述，并将 FR-021 改为产品视角的“本地数据服务”，不再规定 localhost HTTP。PRD 与全栈 TypeScript、类型化 IPC 的技术决策冲突已经关闭。

当前架构仍只完成第一块、同名旧架构仍存在，数据正确性、Skill 文件事务、IPC 契约、性能预算、升级恢复和 AI 数据边界尚无可实施设计，因此仍不能作为 Codex 全面编码的唯一依据。

## 3. Findings

### F-01 [P1] 架构文档尚未形成可实施闭环

- **类型：** 缺失章节，不是现有架构方向缺陷。
- **受影响章节：** `5. 分块生成状态` 及其声明的后续全部章节。
- **问题：** 当前文档只有背景、约束、驱动因素和顶层形态，缺少组件、数据、接口、运行、部署、测试和演进设计。
- **为什么重要：** 单人依赖 Codex 实施时，未定义的边界会被编码阶段临时决定，容易造成 schema、IPC、任务恢复和错误语义不一致。
- **证据：** 架构文档第 5 节明确写明“本次已完成第一块”，下一块才展开限界上下文、采集内核和 SQLite 设计。
- **修订方向：** 完成组件视图、数据视图、接口视图、运行时视图、部署视图、可观测性、测试策略、风险和演进路线后再申请架构批准。

### F-02 [已关闭] PRD FR-021 未同步类型化 IPC 决策

- **原问题：** PRD v2.1/v2.2 将 localhost HTTP API 定义为 MUST，与 ADR-003 和架构的类型化 IPC 冲突。
- **关闭证据：** PRD v2.3 将 FR-021 改为“本地数据服务”，验收标准只描述 Dashboard 可查看数据、离线可用以及采集随客户端生命周期启动和停止，不再规定 HTTP、回环地址或具体通信协议。
- **关闭结论：** 产品需求与技术决策的职责边界已经恢复；具体实现继续由 ADR-003 和架构文档定义。
- **后续动作：** 架构设计文档修订时将输入基线从 PRD v2.1 更新为 PRD v2.3。

### F-03 [P1] 存在同名旧架构，且内容与当前范围冲突

- **类型：** 文档配置管理缺陷。
- **受影响文件：** 根目录 `TrustTools-V3.0-架构设计文档.md` 与 `docs/design/TrustTools-V3.0-架构设计文档.md`。
- **问题：** 两个同名文件内容和版本不同。根目录 v1.0 仍包含浏览器插件、旧模块和旧部署路径；`docs/design` 下 v2.0 已明确浏览器插件不在 V1 范围。
- **为什么重要：** Codex、评审者和未来贡献者可能读取错误文件并实现已废弃范围。
- **证据：** 两文件校验值和行数不同，分别为 v1.0 与 v2.0；旧文档包含“浏览器插件链路”。
- **修订方向：** 指定 `docs/design/TrustTools-V3.0-架构设计文档.md` 为唯一现行架构；将根目录旧文档移动到归档目录并标记“已归档”，或删除重复文件；在项目总览中链接唯一基线。

### F-04 [P1] 最高优先级的 Token 采集正确性尚无详细设计证据

- **类型：** 缺失决策证据。
- **受影响章节：** 架构 `3.1`、`QA-01`、`QA-02`、`2.4 TokenTracker 参考边界`。
- **问题：** 文档提出事务化采集、稳定事件身份、测量语义和 checkpoint 同事务，但未定义 Source Adapter contract、规范化 fact schema、幂等键组成、快照转增量规则、截断/替换算法、checkpoint 状态机和失败重放边界。
- **为什么重要：** Token 准确率是 P0 驱动；这些规则若在各 Provider 内自行发挥，会产生重复计费、漏计和不可解释差异。
- **证据：** ADR-009 至 ADR-012 已记录原则，但当前架构尚未把原则落成组件、数据约束和事务时序。
- **修订方向：** 增加采集内核组件图和时序图；定义 `SourceObservation → NormalizedUsageFact → AcceptedFact + Checkpoint` 流程、唯一约束、测量语义、重放策略和 Provider golden fixtures。

### F-05 [P1] Skill 安装、更新、删除和恢复缺少统一文件事务模型

- **类型：** 缺失设计。
- **受影响需求：** FR-007、FR-009、FR-014、FR-015 及架构 `QA-05`。
- **问题：** 尚未定义下载暂存、压缩包限制、路径穿越与符号链接处理、静态扫描门禁、多目标安装、原子替换、部分失败补偿、垃圾桶恢复、版本更新和“保留本地修改”的冲突策略。
- **为什么重要：** 这些操作会直接改写用户本地 AI 工具目录；半成功或错误覆盖可能损坏用户资产，并造成 SQLite 状态与文件系统不一致。
- **证据：** 顶层架构只写“下载暂存、原子安装、回滚”和恶意包场景，没有事务状态机、恢复日志和冲突结果。
- **修订方向：** 建立统一 `FileOperationPlan` 和持久化操作日志；采用预检、暂存、验证、提交、补偿五阶段；明确跨目录操作不是数据库原子事务，并设计幂等恢复与人工处置状态。

### F-06 [P1] AI 审查的 MUST 需求与“条件接受”决策未闭合

- **类型：** 未决产品与架构决策。
- **受影响需求与决策：** PRD FR-009、架构 `2.5`、ADR-008。
- **问题：** PRD 把静态扫描加 AI 审查列为 MUST；ADR 将 AI 保持条件接受，默认供应商、数据出机范围、成本承担方式均未确定。
- **为什么重要：** 无法确定 V1 验收标准，也无法证明“本地优先、不上传完整对话/源码”的隐私承诺。
- **证据：** 架构图将 AI Adapter 标为“隐私策略待确认”，ADR-008 要求产品确认后才能绑定默认云端供应商。
- **修订方向：** 产品必须二选一：将 V1 MUST 改为本地静态扫描、AI 为用户显式启用的增强项；或明确 AI 服务、发送字段、脱敏、授权、保留期、配额、超时、降级和退出开关，并新增正式 ADR。

### F-07 [P1] 性能与资源目标缺少可验证预算

- **类型：** 缺失证据。
- **受影响需求与章节：** NFR 性能目标、架构 A-03、A-05 和 `3.1`。
- **问题：** `<200MB`、首次两分钟可见、页面和查询响应目标没有分配到 Renderer、Main、Utility、SQLite、扫描任务和缓存，也没有定义样本规模、冷/热状态和目标设备。
- **为什么重要：** Electron 总内存低于 200MB 的可行性置信度已被架构标记为低；不提前验证可能在发布前才发现不可达。
- **证据：** A-05 仅要求签名安装包实测，尚无 PoC 结果、基线设备或失败后的产品降级规则。
- **修订方向：** 建立质量属性预算和 Architecture Fitness Tests；锁定最低/典型设备、样本集、测量窗口、进程口径和 P95 阈值；在全面 UI 开发前完成签名包内存与五类 P0 Provider 首扫 PoC。

### F-08 [P2] IPC 与后台任务运行语义不完整

- **类型：** 局部设计缺失。
- **受影响章节：** 架构 `4.2`、`QA-06`、ADR-002、ADR-003。
- **问题：** 已选择 contextBridge、IPC 和 MessagePort，但未定义 contract 版本、错误码、超时、取消、进度、背压、大消息限制、Utility 重启后的任务恢复及连续失败阈值。
- **为什么重要：** 扫描、导入、安装等长任务容易出现 UI 假死、重复执行、事件丢失或无限重启。
- **修订方向：** 增加命令/查询/事件三类契约、统一 envelope、任务 ID、取消和恢复语义；规定负载上限、分页/流式策略和 Utility supervisor 状态机。

### F-09 [P2] 数据生命周期、迁移、备份与恢复未定义

- **类型：** 缺失运行与数据设计。
- **受影响章节：** SQLite 设计、隐私目标、桌面升级流程。
- **问题：** 没有数据库 schema 版本、迁移事务、失败回滚、损坏检测、重建策略、数据保留、用户重置、导出和诊断包隐私规则。
- **为什么重要：** 本地单一事实源一旦升级失败或损坏，会影响全部功能；无限保留数据也与隐私和磁盘控制目标冲突。
- **修订方向：** 定义 migration manifest、启动前备份/检查、可重建表与不可重建表、保留策略、全量重置和隐私安全导出；为迁移失败设计只读恢复模式。

### F-10 [P2] 模块边界只有原则，没有可执行守护

- **类型：** 缺失实施机制。
- **受影响章节：** 架构 `3.3`、`4.3`、`4.4`。
- **问题：** 文档要求六个上下文不共享内部表结构，但物理上共用 SQLite 和 Utility Process，尚未定义 schema 所有权、跨域查询、事件发布提交时机和禁止依赖规则。
- **为什么重要：** 单仓库和 AI 生成代码容易绕过 Application Service 直接访问其他模块 repository，最终形成隐式耦合。
- **修订方向：** 为每个模块定义公开 contract、表前缀/所有权、跨域 read model 和事务边界；用 ESLint/依赖图测试和 repository 导入规则执行守护。

### F-11 [P2] 发布、签名、自动更新和回滚路径不完整

- **类型：** 缺失部署与运维设计。
- **受影响章节：** ADR-007、Desktop Platform 边界、PRD 分发依赖。
- **问题：** 已选择 electron-builder，但没有制品来源、代码签名、公证、更新清单签名、分阶段发布、降级兼容、原生 addon ABI 验证和失败回滚流程。
- **为什么重要：** macOS/Windows 双平台和原生 SQLite addon 会把发布链路变成实际运行风险；错误更新可能使客户端无法启动或无法打开数据库。
- **修订方向：** 增加构建矩阵、制品校验、签名/公证、更新通道、数据库前向兼容规则、回滚限制和发布门禁。

### F-12 [P3] 规模假设缺少来源和触发依据

- **类型：** 假设证据不足。
- **受影响章节：** A-03。
- **问题：** “三年不超过 1000 万条”和“500 万条复测”未说明由哪些 Provider、日活会话量和事件粒度推导。
- **为什么重要：** 错误规模假设会影响索引、聚合、清理和备份设计，但当前不阻塞顶层架构。
- **修订方向：** 用重度用户场景建立容量模型，记录日事件量、增长率、平均记录大小、聚合周期和磁盘上限。

### F-13 [P3] AI 与自动化代码开发缺少治理证据模板

- **类型：** 可维护性改进项。
- **受影响章节：** 架构 `3.3 单人 + Codex 的组织驱动`。
- **问题：** 文档要求 ADR、测试证据和人工批准，但未规定 Provider 来源研究、生成代码审查、许可证检查和发布批准的证据格式。
- **为什么重要：** 项目计划开源，且参考外部项目的数据获取行为；缺少可追溯证据会增加来源争议和维护风险。
- **修订方向：** 建立来源研究记录、Clean Room 实现清单、fixture 来源登记、相似度审查和发布签核模板。

## 4. 已接受的权衡

以下内容属于有依据的架构选择，不应作为缺陷处理：

1. **模块化单体而非本地微服务：** 与单人维护、单机事务和单发布单元匹配。
2. **多进程而非全部放入 Electron Main：** 增加 IPC 成本，但显著降低重任务阻塞窗口生命周期的风险。
3. **统一 SQLite 单写者：** 牺牲任意并行写入，换取一致性、迁移和备份的简单性。
4. **类型化 IPC 而非 localhost HTTP：** 当前没有跨设备或独立部署需求，避免端口和本地 HTTP 攻击面。
5. **被动采集加周期对账：** 牺牲部分实时性，换取对第三方工具更低侵入。
6. **TokenTracker 仅作行为研究：** 固定参考版本并重构 contract、schema、接口和测试，符合独立开源目标。

## 6. 测试性与运维性审查

### 6.1 必须补充的架构测试入口

- Source Adapter contract tests：追加、截断、替换、重复、乱序、损坏和 schema 变化。
- 数据正确性 tests：event、delta、snapshot、estimate 四种测量语义及跨源去重。
- SQLite tests：事务原子性、迁移、崩溃恢复、WAL、百万级查询和数据库损坏恢复。
- IPC contract tests：schema 兼容、超时、取消、背压、Utility 重启和错误映射。
- Skill 文件事务 tests：恶意压缩包、部分安装失败、恢复、更新冲突和本地修改保护。
- 发布 smoke tests：目标平台签名包启动、原生 addon 加载、升级迁移和离线降级。

### 6.2 必须补充的运行证据

- 本地结构化日志字段、敏感字段清洗规则、轮转和磁盘上限。
- Provider 新鲜度、最后成功 checkpoint、降级原因和重试状态。
- Utility Process 退出原因、重启次数、任务恢复状态和安全停机条件。
- 数据库版本、迁移结果、完整性检查和只读恢复模式。
- 市场与 AI 外部调用的超时、重试、熔断和用户可见降级状态。

## 7. 修复优先级

### Gate A：继续架构设计前

1. 归档同名旧架构，指定唯一现行文档。
2. 决定 AI 审查的 V1 产品边界。

### Gate B：进入核心编码前

1. 完成 Token 采集内核、schema、事务和恢复设计。
2. 完成 IPC 契约和 Utility supervisor 设计。
3. 完成性能容量预算及关键 PoC。
4. 定义模块 contract、数据所有权和架构守护规则。

### Gate C：开发 Skill 与发布能力前

1. 完成 Skill 文件事务和供应链安全设计。
2. 完成数据库迁移、备份、重置和数据保留设计。
3. 完成签名、升级、回滚和双平台发布设计。

## 8. 复审通过标准

满足以下条件后可重新提交 architecture-audit：

- P1 Findings 全部关闭，或由产品负责人以 ADR 明确接受风险和期限。
- 架构文档不再标记为仅完成第一块。
- PRD、ADR、架构文档对语言、进程边界、通信方式和 AI 范围表述一致。
- Token 采集、Skill 文件操作和 SQLite 升级均具备状态机、失败路径和测试入口。
- 关键 NFR 具有明确测量口径、目标设备、数据集和自动化门禁。
- 目录中只有一个现行架构基线，历史版本明确归档。
